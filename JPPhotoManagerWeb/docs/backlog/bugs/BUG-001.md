# BUG-001 — Album add/remove assets: unbounded id list drives one SQL statement per id

- **Steps to reproduce:** (inferred from code review; not yet reproduced at runtime)
  1. Authenticate and create a manual (non-smart) album.
  2. `POST /api/albums/{id}/assets` with a body such as `{"assetIds": [1, 2, 3, … 50000]}` (and, separately, `{"assetIds": [null]}`).
  3. Repeat with `DELETE /api/albums/{id}/assets`.
- **Expected:** a sane upper bound on the list is enforced (400 above it), null elements are rejected, and membership is added or removed with a bulk statement rather than one statement per id.
- **Actual:** `AlbumAssetIdsRequestDto.assetIds` is only `@NotEmpty`, with no `@Size` bound and no `@NotNull` on elements. `AlbumRepositoryImpl.addAssets()` calls `existsAsset` plus `addAsset` for each id, and `removeAssets()` one delete per id, all in one transaction — tens of thousands of statements for a large list; a `null` element is passed through to the repository.
- **Environment:** both — request-validation and persistence defect, independent of the deployment.
- **Notes:** `JPPhotoManagerWeb/backend/src/main/java/com/jpablodrexler/photomanager/infrastructure/web/dto/request/AlbumAssetIdsRequestDto.java:8`; `.../infrastructure/persistence/adapter/AlbumRepositoryImpl.java:75-88`. Suggested fix: `@Size(max = …)` and `List<@NotNull Long>` on the DTO, plus bulk `INSERT … SELECT … WHERE NOT EXISTS` / `DELETE … WHERE asset_id IN (…)` in the adapter. Assets are not user-owned in this domain, so this is a robustness/performance issue, not an access-control gap. Found by the `code-reviewer` scoped review of 2026-10-04 (findings 🟡 #1 and #2, which share one cause).
