# BUG-002 — Album list is N+1: one count query per album

- **Steps to reproduce:** (inferred from code review; not yet reproduced at runtime)
  1. As one user, create many albums (e.g. 50), including several smart albums with a filter.
  2. Load `/albums` (or call `GET /api/albums`) with SQL statement logging or a query counter enabled.
- **Expected:** a constant, small number of queries regardless of how many albums exist (e.g. one grouped count query, with smart-album totals computed lazily or only when needed).
- **Actual:** `GetAlbumsUseCaseImpl.execute()` maps every album through `countAssets(album)`: one `countAssets` query per manual album, and for each smart album it builds an `AssetFilter` and runs a full filtered `findSmartAlbumAssets(filter, 0, 1)` query only to read `total()`. The list costs 1 + N queries (more for smart albums).
- **Environment:** both — query-shape defect, visible as latency that scales with the number of albums.
- **Notes:** `JPPhotoManagerWeb/backend/src/main/java/com/jpablodrexler/photomanager/application/usecase/album/GetAlbumsUseCaseImpl.java:27-37`. The same smart-vs-manual count branch is duplicated in `UpdateAlbumUseCaseImpl.java:30-36` — worth extracting when fixing this. Found by the `code-reviewer` scoped review of 2026-10-04 (finding 🟡 #3).
