# BUG-003 — Albums backend code-quality nits: duplicated count logic, inline page assembly, missing 404 in OpenAPI

- **Steps to reproduce:** (code-review findings; no runtime symptom)
  1. Compare `GetAlbumsUseCaseImpl.countAssets()` with the count branch in `UpdateAlbumUseCaseImpl.execute()`.
  2. Read `AlbumController.getAlbum()` (the `new PaginatedData<>(…)` block).
  3. Read `AlbumController.createAlbum()`'s `@ApiResponses`.
- **Expected:** one shared implementation of the "count a smart or manual album's assets" rule; controllers only delegate and return (`code-reviewer` §1.1), with response mapping in `AlbumWebMapper`; and `@ApiResponses` listing every reachable status (§3.4).
- **Actual:** (a) the smart-vs-manual count branch is written twice (`GetAlbumsUseCaseImpl.java:37-43` and `UpdateAlbumUseCaseImpl.java:30-36`) and can diverge; (b) `getAlbum` builds `PaginatedData<AssetResponseDto>` inline in the controller (`AlbumController.java:94-97`) instead of in `AlbumWebMapper`; (c) `createAlbum` documents 201/400/401 but not 404, although `CreateAlbumUseCaseImpl` can throw `UserNotFoundException`, which `GlobalExceptionHandler` maps to 404.
- **Environment:** both — no behavioural difference; (c) affects only the generated API docs.
- **Notes:** best done together with BUG-002, which rewrites the same count logic — extract it once into `AlbumAssetFilterFactory` or a small collaborator and reuse it in both use cases. For (c), add `@ApiResponse(responseCode = "404", description = "User not found")`. Found by the `code-reviewer` scoped review of 2026-10-04 (findings 🟢 #1-#3).
